CM4 · BattleManager 重构评审与拆分建议

基于 CM4-A1 / CM4-A2 审计结果与 core/battle-manager.js（约 6220 行）静态分析，给出设计原则符合度、可拆分区与推荐 PR 顺序。

日期：2026-08-11 对象：core/battle-manager.js 基线：B3-FINAL（不可变） 性质：评审建议（未改代码）

一、CM4 设计原则摘要

CM4 阶段从「生成前沿研究」转向「生产系统审计」，其边界在 docs/CM4/README.md 中写死：只审计生产级核心组件的正确性、健壮性、可维护性与一致性，产出可执行的修复清单，不改 B3-FINAL 生成链路。落到 BattleManager 上，可提炼为五条原则：

原则含义来源
P1 基线不可变B3-FINAL 冻结参数、生成链路、验收门槛均不可改动；只允许修核心系统本身。CM4 README / project memory
P2 最小侵入重构以低回归风险为先，结构改动优先于行为改动，避免破坏现有对局节奏。工程约定
P3 单一数据源模块化要求单一数据源、清晰接口、无冗余依赖；反对「以文件切分代替逻辑解耦」。硬约束
P4 降级完备核心代码必须 try-catch、DOM 存在性检查、空实现降级。硬约束
P5 关注点分离决策（AI）、状态（所有权/计分）、配置（Boss/人格）、机制（必杀/拦截）各自独立演进。审计方法论

关键约束：AIPlayerCore 不是独立机器人，而是把 think() 全部委托给内部 _rater（即 TechRater）的「行为壳」。任何拆分都必须维持这条委托链，否则会破坏 think() 的逐级回退与 execute() 的状态同步。

二、Battle 规则（三点连线 Boss 战 v2.0）

主线 Boss 战由 ThreePointLineManager（core/three-point-line-manager.js）承载全部规则判定，TplBattleController 桥接 AI 与 UI。规则核心是一套「据点 + 四维度争夺」的领地博弈，而非单纯的填空比快。以下按胜负链路、归属仲裁、据点机制、对战节奏四层展开。

1. 胜负链路（v2.0 6.x，四条路径）

路径触发条件判定
A 三点连线绝杀棋盘满 + 占领据点数领先对方（≥1）领先方进入「可连线」等待，可手动/AI 连线直接绝杀；落后方无此选项，防翻盘失衡
B 全局解题棋盘满 + 选择不绝杀 / 据点持平或均无据点按永久归属格多者胜；持平按失误少者胜
C 强制结算迁移失败 + 棋盘满 + 无人达成 A/B据点数 → 失误数 → 归属格数 → 平局
满盘即时任一方填满非固定格触发 GAME_END，结算同 B/C

2. 归属仲裁（谁填的算谁的）

规则说明
永久归属填对数字 → 该格永久归己方（_playerOwned/_aiOwned），另一方可透过「幽灵格」抢占
幽灵格抢占对方填错的格落入红叉窗口（2.5s/4s/6s，连续错误递增），窗口内可抢占，抢对则易主、抢错则格子恢复空白并记己方失误
错误锁定己方填错格在锁定期间不能再填，对方可抢；任意一方填对后自身连续错误计数清零
拒绝情形固定格、已被永久归属且非抢占、已实填且非抢占，均返回失败事件

3. 据点机制（胜利的核心争夺单元）

规则说明
据点构成据点 = 1 个核心格定位 + 四个争夺维度（行 row / 列 col / 宫 box / 笼 cage，DIMS）
隐匿与显现城堡（第 1 据点）开局可见；2 个隐藏据点需核心格被填对才显现
维度占领某维度一方填对数 > 维度空格数一半 → 永久占领该维度（不可抢回）
据点占领一方占领 ≥3 维度 → 永久夺下据点；2:2 平局 → 据点迁移到干净位置
迁移失败无干净迁移位 → 进入强制结算路径 C

4. 对战节奏

项说明
AI 步进AI 通过 think()（委托 TechRater）选格，经 tpl.onAIFill 仲裁后落盘；AI 落子对玩家不可见（幽灵格样式，防作弊），仅标记 isAiFilled/_aiNum/_aiMistake
AI 绝杀决策可连线时：领先 → 立即连线；落后 → 放弃连线走全局解题；持平 → 50% 概率连线
速度调节基础速度 speedMin/speedMax；首次行动加速（0.6–1.3s）；连对 3 次动态错误率 ×0.8
事件通知据点显现/维占领/据点占领/迁移/绝杀/结算等均经 TPL_EVENTS 上报 UI，控制器只做透传与结算封装
规则要点：绝杀是「领先方」的主动终结权而非自动获胜——棋盘满且据点领先时，需连线才算绝杀，否则落回全局解题。因此对局胜负往往由「据点争夺 + 归属格数 + 失误数」三重口径叠加决定，而非单纯比谁填得快。

三、BattleManager 当前符合度

✅ 保留（与原则一致，重构时不应破坏）

项说明对应原则
✅ 统一事件出口 全部回调经 _emit(event, data) 且 try-catch 包裹，UI 只消费事件，反向调用少。P4
✅ 降级路径 TechRater 缺失→_aiMoveLegacy；think() 返 null→回退；WeightedScore 缺失→格子计数。P4
✅ 决策壳委托 AIPlayerCore 只做性格/策略/心理战，解题由 _rater 承担，职责清晰。P5
✅ 配置成块 BOSS_CONFIGS 与 AI_PERSONALITIES 为纯数据块，与类逻辑边界清晰。P3
✅ 版本注释 关键改动带 V4.x 标记，回滚与审计成本低。P2

⚠️ 风险（可运行但脆弱的耦合，重构重点）

项说明位置
⚠️ 巨型方法 onPlayerFill（约170行）、_applyAiMove（约140行）、_initBossMechanisms（约150行）单方法负担过重。M1
⚠️ 私有字段跨类读 BattleManager 直接读 _aiPlayer._rater / _noteAttentionMap / _personality，跨类耦合脆弱。M4 / CM4-A2
⚠️ 三运行环境不一致 单机 / tpl / duel 对同一套人格接口消费方式不同（setGameState、execute()、note 分支），行为迥异。I1/I2/I3
⚠️ 魔法数字 连击 2/3、震慑 1500/2000、专注 ±3/20、忍杀 3500 等裸数字未成常量体系。M2
⚠️ 异步清理不全 stop() 未清理全部 setTimeout（_stunPlayer、_skillGuanJu 等），stop 后仍改写状态。R2/R5

❌ 违反（应优先通过拆分矫正）

项说明位置
❌ 状态写入分散 所有权转移、计分、专注、连击在 _applyAiMove 与 onPlayerFill 各写一份，逻辑重复且不对称（AI 抢玩家格不回退 playerScore）。C4 / C5
❌ 双套预警系统 _checkWarningTriggers 与 _aiMoveLegacy 各自硬编码预警阈值，行为不一致。S1
❌ 必杀技空结果卡死 _skillQuanTao/_skillTianDao 在 results 为空时 _aiThinking 永 true，AI 整局僵死。C1 / C2
❌ 状态标志重叠 _warningTriggered 与 _warning60/70Triggered 三个标志职责重叠。S2

四、不应该拆的部分

以下片段强耦合于同一时序或同一数据源，强行外抽会引入「以文件切分代替逻辑解耦」的反模式（违反 P3）：

  • AI 走棋时序：_aiMove → _aiMoveWithRater → _applyAiMove → _scheduleAiMove 是同一思考/落子/调度闭环，拆开会破坏暂停与 _aiThinking 复位逻辑。
  • 委托链：AIPlayerCore 的 think() → _findAllVisibleResults → _rater 与 execute() → _rater._fillCell 必须捆绑，否则逐级回退与状态同步失效。
  • Boss 专属机制：lockCells、battleTuning.isKiller、幻影格与对应 Boss 关卡数据是绑定的，不应与通用计分混提。
  • 性格调整逻辑：_initAiPlayer 里 aiDifficulty 对人格的修改与人格选择耦合，拆出单独关心会丢失「按 Boss 叠加难度」的语义。
  • 计分-专注-胜负链：_calcFillPoints → _onFillFocusEval → _checkWin 互相调用，属同一账本，拆散易造成计分口径漂移（CM4-A1 已指出 breakdown 与实时分不一致）。

片段抽出方式风险

AI_PERSONALITIES（403–660行）独立配置模块，保留内部引用低（纯数据）

PR-1 纯结构调整

目标

在零行为变化前提下，清除最易出错的结构负担：从 battle-manager.js 抽出 BATTLE_EVENTS 常量、cellTag 工具、TechRater 引导加载器，并修正 CM4-A1 中标注的「clearInterval 清 setTimeout」等笔误级问题。

验收

node 测试脚本 test-battle-manager.js / test-battle-mechanics.js 全绿；import 面不变；无逻辑改动。

PR-2 配置分离

目标

把 BOSS_CONFIGS 与 AI_PERSONALITIES 两块纯数据迁到独立配置模块，保留原导出名与结构。这是「单一数据源」（P3）的直接落地，也为后续参数扫描（如 Boss 战调参）提供独立改入口。

验收

game.html 与所有脚本 import 路径更新后行为不变；Boss战调参结果.md 中的旋钮（interceptProbability / stealPriority / focusGain）在配置文件中可寻址。

PR-3 AI strategy extraction

目标

把 AIPlayerCore 的决策链（think、_determineStrategy、_writeNote、心理战、观察器）与 BattleManager 的状态管理解耦：让 BattleManager 只负责调度与落地，AI 只负责「下一步选哪里」。同时对齐 CM4-A2 的 I1/I2/I3 三处接口契约（单机注入 setGameState、修复 _moveCount 冻结、补 note 分支）。

验收

单机 / tpl / duel 三套运行环境对同一对局给出相同决策；CM4-A2 三个 P1 均有对应修复。

PR-4 state reducer

目标

把所有权转移、计分、专注、连击收敛到单一「状态变更入口」（类似 reducer），消除 _applyAiMove 与 onPlayerFill 的重复写入与不对称（C4 AI 抢格不回退玩家分）。此步依赖 PR-3 完成的 AI/状态边界。

验收

计分口径唯一；getScoreBreakdown 与实时分一致；抢格/撤销的 pts 对称（C5）。

PR-5 拆分建议（后续方向）

目标

在 PR-1~4 稳定后，按需把巨型方法（onPlayerFill、_applyAiMove、_initBossMechanisms）按职责拆为私有方法，并抽魔数常量表。此步为可选项，仅在确有维护痛点时进行。

原则

每次拆分都必须保持「同一时序、同一账本」的完整性；以「能否独立测试」为拆分合法性判据，而非「文件变短」。

总体判断：BattleManager 的骨架（事件出口、降级、决策壳委托）符合 CM4 原则，值得保留；主要负债集中在「状态写入分散」与「单机/脚本运行环境行为不一致」两处。推荐的 PR-1→PR-4 顺序是「先易后稳」——先清结构、再切配置、再拆 AI/状态边界，每步都保持行为可回归，符合 CM4 最小侵入与基线不可变两条硬约束。
